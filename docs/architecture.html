review-approval-temporal

System architecture

Two front doors share one business-logic layer, which issues a direct read or a Temporal signal — and, on the write path, waits for that signal's effect to actually land in Postgres before it answers the caller.

direct call, awaited Temporal-mediated, eventually consistent Keycloak — auth, out of band

Deployable units

bff
One process, one image: uvicorn review_approval.app:app serves bff/ui.py, api/routes.py, and /sandbox/* together — not split by front door.
worker-workflow
python -m review_approval.workflow.worker, WORKER_MODE=workflow. Executes workflow code only — never opens a Postgres connection.
worker-activity
Same entrypoint, WORKER_MODE=activity. The only code in the system permitted to write to Postgres, via one activity per state change.
Postgres
One instance, two databases: review_approval (drawn above — this app's queryable record) and a separate temporal database used only by Temporal Server's own internal persistence, never touched by application code.
Keycloak
Operator/Manager are plain realm roles, gating which screen a session can see. The five mutating actions are Resources, not roles — checking one always costs a live UMA call, by design; there is no permission-result caching yet.
Redis
Server-side store for /ui/* only, called directly by bff/ui.py/bff/keycloak_session.py — never through workflow/service.py, and never touched by api/routes.py. ui-session:<id> holds the login (tokens + transparent refresh); the separate ui-memory:<id> holds bulk-selection state and a pagination resilience fallback (workflow/memory_service.py's SessionMemory). Both expire on the same sliding 30-minute idle TTL and are deleted together on logout.
